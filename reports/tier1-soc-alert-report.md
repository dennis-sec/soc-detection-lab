# SOC Tier 1 Alert Triage Report — Drupalgeddon2 Exploitation Attempt

**Analyst tier:** Tier 1 (alert triage and escalation)
**Report type:** Alert triage / escalation
**Date of analysis:** 29 July 2026
**Status:** Escalated to Tier 2

> Note: this is a simulated-incident report from a controlled home lab. The attack was generated by me against my own isolated, deliberately vulnerable target to produce realistic telemetry. The report is written strictly from a Tier 1 analyst's viewpoint — triaging the alert using only what the monitoring stack surfaced, then escalating. No response actions (containment, eradication, recovery) were performed; those are Tier 2/3 responsibilities and are flagged for escalation below.

## 1. Alert Summary

A high-priority Suricata IDS alert fired in the Wazuh SIEM indicating an attempted remote code execution against an internal web server.

- **Alert source:** Suricata IDS (LAN sensor), forwarded to Wazuh
- **Signature:** `ET WEB_SPECIFIC_APPS Drupalgeddon2 <8.3.9 <8.4.6 <8.5.1 RCE Through Registration Form (CVE-2018-7600)`
- **Signature ID (SID):** `2025534`
- **Alert classification:** Attempted Administrator Privilege Gain
- **Alert time:** 29 July 2026, 15:27:06 – 15:27:12
- **Source IP:** `10.10.10.100`
- **Destination IP:** `10.10.20.100` (Apache / Drupal 7 web server)
- **Destination port:** 80 (HTTP)
- **Protocol:** TCP

## 2. Triage — True Positive or False Positive?

**Assessment: TRUE POSITIVE (high confidence).**

Reasoning from the available telemetry:

- The signature is **exploit-specific**, not a generic anomaly — it matches the request pattern of a known, named vulnerability (Drupalgeddon2, CVE-2018-7600), not benign traffic that merely looks unusual.
- The **destination is a Drupal 7 web server**, which is the exact software the exploit targets — the alert is contextually consistent, not a mismatched signature.
- The exploitation alert was **preceded by reconnaissance** from the same source IP (see Investigation), which fits a real attack sequence (scan → identify → exploit) rather than isolated noise.
- The alert classification ("Attempted Administrator Privilege Gain") and the HTTP-to-port-80 delivery align with how this exploit is actually delivered.

There is no indication this is a scanner false positive or a benign application behaviour.

## 3. Investigation Summary

Reviewing surrounding events in the SIEM from source `10.10.10.100`:

- **Prior reconnaissance (same source):** At 14:49, a TCP SYN port scan from `10.10.10.100` fired the custom rule `SID 1000001` ("LOCAL Nmap SYN Scan Detected"). Shortly after, multiple `SID 2024364` alerts ("ET SCAN Possible Nmap User-Agent Observed") hit port 80 — consistent with the attacker enumerating the web service before exploiting it.
- **The exploitation alert itself (15:27):** the Drupalgeddon2 signature (`SID 2025534`) fired against the Drupal server on port 80.
- **Post-exploitation activity on the host:** **not visible from available telemetry.** There is no endpoint agent on the target, so any commands executed, files accessed, or privilege changes on the host would not appear in the SIEM. This is a known visibility limitation and is the basis for the escalation below.
- **Corroborating indicator of compromise:** shortly after the exploitation alert, the pfSense firewall logged **repeated blocked outbound DNS attempts** from the target (`10.10.20.100` → `1.1.1.1:53` and `9.9.9.9:53`). A healthy internal host does not normally have its outbound traffic denied; repeated blocked egress from a single host immediately after an RCE alert is a strong secondary signal that the host may have been successfully compromised and attempted to communicate outbound.

## 4. Indicators of Compromise (IOCs)

- **Source IP:** `10.10.10.100` (origin of scan and exploit)
- **Targeted host:** `10.10.20.100` (Drupal 7 web server)
- **Vulnerability exploited:** CVE-2018-7600 (Drupalgeddon2)
- **Firing signatures:** SID `2025534` (exploit), SID `1000001` (recon scan), SID `2024364` (web enumeration)
- **Suspicious outbound destinations (blocked):** `1.1.1.1:53`, `9.9.9.9:53` (DNS) from the targeted host

## 5. Severity and Priority Assessment

**Severity: HIGH.**

Justification:
- The alert is an **attempted remote code execution** against a server — a critical exploit class — not low-level noise.
- It is a **confirmed-vulnerable target** (Drupal 7, in the affected version range for CVE-2018-7600), so successful exploitation is plausible, not theoretical.
- The **blocked outbound attempts** immediately afterward raise the likelihood that exploitation succeeded and the host attempted to act.
- Successful exploitation of this CVE yields code execution as the web-server user, a realistic foothold for further compromise.

The combination of a high-confidence exploit alert against a vulnerable host, plus a corroborating post-alert IOC, warrants prompt escalation rather than closure at Tier 1.

## 6. Recommendation and Escalation

This alert exceeds Tier 1 scope and is **escalated to Tier 2** for deeper investigation and response. Recommended next steps for the receiving tier:

1. **Investigate the target host (`10.10.20.100`) directly** — Tier 1 cannot confirm what happened on the host because no endpoint telemetry exists. Host-level examination (processes, new accounts, file changes, web-server and auth logs) is required to confirm whether exploitation succeeded and determine the extent of compromise.
2. **Treat the host as potentially compromised** pending that investigation, given the blocked-egress IOC.
3. **Contain if confirmed** — network isolation / takedown of the affected host is a Tier 2/3 response action.
4. **Preserve evidence** — the firing SIEM alerts, the firewall egress logs, and the relevant Suricata events have been noted above for the responding analyst.

### Tier 1 observations for detection improvement (informational)

- **No host visibility on the target.** The most significant gap surfaced during triage: everything after the network-level exploit attempt is invisible to the SIEM. Deploying endpoint telemetry (an agent, or agentless log forwarding for legacy hosts) would let a future analyst confirm compromise without escalating blind.
- **Blocked egress is not currently an alert.** The denied outbound DNS was only found by manually reviewing firewall logs. A dedicated SIEM rule for repeated blocked outbound from an internal host would surface this IOC automatically.

**Outcome:** True positive, High severity, escalated to Tier 2 for host investigation and potential containment.
